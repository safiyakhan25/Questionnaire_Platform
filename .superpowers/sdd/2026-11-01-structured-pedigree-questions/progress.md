## Final whole-branch review (Opus, fresh subagent)

Package: `.superpowers/sdd/2026-11-01-structured-pedigree-questions/review-{backend-main,backend-tests,frontend}.diff`, scoped to exactly the files this plan touched (not the whole staged tree, which also carries the unrelated earlier auth-removal work from this session).

**Verdict: not ready to merge as-is — one Critical, several Important.** Full findings list is in the subagent's report (not reproduced here); re-graded and acted on below. Note: the reviewer's line numbers refer to its concatenated `review-package.diff`, not real source line numbers — verified every finding against the actual files before acting.

### Critical - fixed
**Premature submission of incomplete structured entries.** `StructuredQuestionField.updateField` and `GroupListField.addRow`/`updateRowField` called the parent `onChange` (which triggers an immediate HTTP `submitAnswer`) on *every* keystroke/add, including a brand-new empty row or a half-filled object. Every answer-writer rejects a partial entry outright (e.g. `DiseaseAnswerWriter` requires non-blank `diseaseType`), so in practice **no multi-field structured question, and no GROUP_LIST row, could ever actually be filled in** - the very first partial state always got rejected before the patient could finish typing. Confirmed by reading the actual component code (the reviewer's line numbers pointed at its diff package, not real files, but the substance was exactly right).

Fix: new shared `structuredFieldCompleteness.js` (`isFieldFilled`/`isEntryComplete`) - a row/object is only ever passed to the parent `onChange` once every field it marks `required` has a value. `GroupListField` now holds its rows as local draft state (seeded once from `value`, never resynced from later prop changes - the same uncontrolled-after-mount convention this codebase already uses for RADIO/CHECKBOX/DROPDOWN), so an in-progress incomplete row survives a refetch instead of being wiped by the server's echo (which never includes it, since it was never submitted). Verified RED→GREEN: `GroupListField.test.jsx` (3 new tests: doesn't propagate an incomplete row, propagates once complete, un-propagates if a required field is cleared back out) and `StructuredQuestionField.test.jsx` (2 new tests: doesn't submit until every required field is filled; the old "list" test updated since its old assertion - submit `[{}]` immediately - was exactly the bug). All green.

### Important - fixed
1. **"No" toggle left stale unsaved data in local state.** Switching to "No" submits `null` (correctly deletes server-side), but the local `current` draft wasn't cleared, so switching back to "Yes" showed fields the server no longer has an answer for. Fixed: `handleNo` now also resets `current` to `{}`. Test: `StructuredQuestionField.test.jsx` "switching to No then back to Yes does not resurrect the unsaved draft".
2. **`ConfigurationValidator` allowed a STRUCTURED question with no `fieldConfig` at all**, which would later crash `StructuredQuestionField` destructuring `question.fieldConfig.shape` on a null. Fixed: `validateForType` now rejects `STRUCTURED` + null `fieldConfig`. Test: `ConfigurationValidatorTest.rejectsAStructuredQuestionWithNoFieldConfigAtAll`.
3. **`question.text` was never rendered for a STRUCTURED question, and `field.label` was dropped for `FAMILY_MEMBER_SELECT`/`_MULTI_SELECT`/`GROUP_LIST`** - a list question showed a bare "Add" button with no context; the co-twin checkboxes and participant rows had no visible labels. Fixed: `StructuredQuestionField` now renders `question.text` as a heading; `FieldRenderer` wraps those three field kinds in a label/heading using `field.label`. Tests: `StructuredQuestionField.test.jsx` "renders the question text as a heading"; `FieldRenderer.test.jsx`'s FAMILY_MEMBER_SELECT and GROUP_LIST tests now also assert the label text renders.
4. **An empty string from a cleared TEXT/DATE sub-field was submitted as `''`, not `null`** - for a DATE field this flows into `PregnancyOutcomeAnswerWriter`'s `LocalDate.parse('')`, an unchecked exception the controller has no handler for (500, not a clean 400). Fixed on the frontend only (the writer is explicitly out of scope per this plan's Global Constraints) - both `StructuredQuestionField.updateField` and `GroupListField.updateRowField` now store `null` instead of `''`. Test: `GroupListField.test.jsx` "clearing a field to an empty string stores null, not an empty string".
5. **`AdminConfigurationIntegrationTest.creatingAStructuredQuestionPersistsAndReturnsItsFieldConfig` was tautological** - no flush/clear, so `getById` read from the first-level persistence-context cache rather than a real round trip to Postgres, which is exactly why it passed even before the missing `ALTER TYPE question_type ADD VALUE` migration was found (that gap was only caught later, by `StructuredQuestionIntegrationTest`, which does genuinely flush via its multi-step session flow). Fixed: added `entityManager.flush(); entityManager.clear();` between create and getById.

### Important - re-graded and deferred (ledgered, not fixed)
**Per-keystroke resubmission pollutes `DISEASE_CATALOG` with orphaned entries.** Once `diseaseType`'s first character is typed, the row is "complete" (non-blank) by the fix above, so every further keystroke still resubmits, and `DiseaseAnswerWriter.findOrCreateCatalogEntry` creates a new catalog row for each distinct partial string ("B", "Br", "Bre", ...) - all but the final one become permanently orphaned (no `DISEASE` row ends up pointing at them, since every submit fully replaces the subject's disease list). **Re-graded from the reviewer's "Important" to a documented, deferred decision**: the effect is bounded to an internal admin-facing catalog table bloating with garbage names - it does not affect pedigree export correctness (export only ever reads an individual's actual, currently-linked `DISEASE` rows, never the catalog's full extent) and does not corrupt or mislead the patient-facing flow. A proper fix (debounce the structured-field commit, or only commit on blur) is a real, non-trivial behavior change to the "when does this submit" contract this plan already modified once for the Critical fix above, and risks its own new timing bugs if rushed. **Final: Ruling**: deferred rather than rushed into this same pass - cost if wrong: `DISEASE_CATALOG` accumulates garbage rows over time; recoverable later by a cleanup migration or a debounce follow-up, not a data-loss or correctness risk today.

### Minor - deferred (ledgered, not fixed, per the skill's "minors never enter the fix pass")
- `requiredWhen` (conditional required-ness, e.g. adoption's parent-ids field) from the spec is not implemented in the frontend UX (asterisk never conditionally appears) - the server-side writer already enforces the real requirement regardless, so this is cosmetic only.
- Duplicate DOM ids across multiple `GROUP_LIST` rows (each row's sub-fields reuse the same `fieldId`), so a `<label>` click could target the wrong row's input.
- The "Does this apply?" toggle's radio `id`/`name="applies"` is hardcoded - two STRUCTURED object-shape questions on the same template would have their toggles cross-wired. Not currently reachable (every one of the 7 seeded questions is alone in its own template), but a real latent bug if that ever changes.
- `FamilyMemberSelect` has no `.catch` on its fetch, no unmount guard, and fetches once per `GROUP_LIST` row independently (no shared cache) - acceptable for the current scale (a handful of family members, a handful of rows), not for a large family.
- `ConfigurationValidator.validateFieldDef`'s `GROUP_LIST` recursion has no depth limit, though the spec/plan only ever describe one level of nesting.

Updating the record: Task 11's live verification proved the backend contract; it did not and could not substitute for exercising the real per-field submission flow, which is where this session's actual Critical bug lived.
